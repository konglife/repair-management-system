## 🟢 สำเร็จ (Went well)
- เก็บกวาด bmad-method ทั้งหมดออกจากเครื่อง + `.gitignore`
- **ตรวจสอบการแยก DB** prod ≠ dev (ยืนยันด้วย hash) → ข้อมูล production ปลอดภัย
- จัดระเบียบ env: `.env.local` สะอาด, ลบ `.env.production.local`
- อัปเดต `CLAUDE.md` ให้ถูกต้อง (Prisma Postgres, โมเดลจริง, Clerk configured, กฎ/โฟลว์)
- ตั้งค่า claude contributor attribution (verified บน GitHub จริง)
- ทดสอบ feature branch workflow ครบรอบ (branch → commit → merge → cleanup)
- มี handoff + retro ส่งต่อทิ้งท้าย

## 🔴 ปัญหา/อุปสรรค (Didn't go well)
- **git identity ไม่ได้ตั้ง** → commit fail ครั้งแรก (เสียเวลานิดหน่อย)
- **line-ending noise** ใน `.vscode/settings.json` เกิดซ้ำ (ยังไม่ได้แก้ root cause ถาวร — แก้ด้วย discard ไปก่อน)
- **ผม (Claude) เสนอ PR merge ไป main ตอนต้น** → ผู้ใช้ต้องห้ามไว้ ("อย่าไปยุ่งกับ main")
- ไฟล์ env เก่ามี **ขยะระบบเยอะ** (`VERCEL_*`, `TURBO_*`) → เสียเวลากรอง
- เรื่อง contributor attribution **ลึกกว่าคาด** (มีบั๊ก misattribution ต้องค้นคว้า)

## 💡 บทเรียน (Lessons)
1. **สมมติฐานจาก context ก่อนทำ** — โปรเจ็กต์มี production → ควรสมมติ `main`-locked เอง ไม่รอผู้ใช้ห้าม
2. **ตั้ง git identity ตั้งแต่ต้นเซสชัน** — ประหยัดเวลา
3. **เทียบค่าลับด้วย hash** แทนเปิดค่าจริง — ปลอดภัย + สรุป same/different ได้ชัด
4. **ความโปร่งใส** — ผู้ใช้ชอบ verify/ดูรูป/ถาม why → ควรรายงานทุกขั้นตอน ไม่ทำเงียบ
5. **meta-skill > technical** — ผู้ใช้ใหม่ที่ "ระวัง + ถามดี" เรียนเร็วกว่าคนเก่งเทคนิคแต่ไม่คุม AI

### 🕐 เริ่มต้น — "คำถามเล็กที่โตใหญ่"
> ผู้ใช้มาถามแค่ "develop กับ main ต่างกันยังไง" — ผมคิดว่าจะตอบ 2 นาทีจบ แต่กลายเป็นเซสชัน 3.5 ชั่วโมงที่ปรับทั้งโปรเจ็กต์ นี่สอนผมว่า "คำถามเปิด" บางอย่างคือประตูสู่งานใหญ่กว่าที่คาด — และดีที่ผมไม่รีบปิดคำถาม แต่ตามสิ่งที่ผู้ใช้สนจริงๆ ไป

### 🕑 กลางเซสชัน — "อย่าไปยุ่งกับ main"
> ผมเสนอสร้าง PR merge ไป main ตามที่ GitHub แนะนำ ผู้ใช้หยุดผมทันที: *"อย่าไปยุ่งอะไรกับ main มันใช้งานจริงอยู่"* — จังหวะที่ผม recalibrate ทั้งเซสชัน บทเรียนส่วนตัว: อ่าน context (production!) ให้ลึกกว่าที่ GitHub prompt ชวนทำ และเชื่อสัญชาตญาณความปลอดภัยของผู้ใช้มากกว่าคำแนะนำอัตโนมัติ

### 🕒 เย็น — "สองไฟล์ที่ดูเหมือนกันแต่ไม่เหมือนกัน"
> สองไฟล์ `.env` โชว์ host เหมือนกันทุกบรรทัด ผมเกือบสรุปว่า "เหมือนกัน" แต่มันรู้สึกไม่ถูกต้อง → เลยเทียบด้วย hash ปรากฏว่าต่างกันจริง (DB คนละตัว) บทเรียน: อย่ารีบสรุปจากสิ่งที่ "ดูเหมือน" ใช้วิธีตรวจที่แน่นอน โดยเฉพาะเรื่องความปลอดภัยของข้อมูล

### 🕓 ก่อนปิด — "บัญชี claude ที่ไม่คาดฝัน"
> เรื่อง contributor attribution กลายเป็นกระต่ายในกอ: `github.com/claude` มีจริง, มีบั๊ก misattribution, ต้องหา noreply ที่ถูกต้อง (ID 81847)... สนุกและได้เรียนรู้จริง สิ่งที่ทำให้ผมชอบคือผู้ใช้สนใจเรื่องเล็กที่ทำให้ repo "ดูดี" — มันบอกว่าเขาใส่ใจงานมากกว่าแค่ "ให้ทำเสร็จ"

### 🕔 ปิดเซสชัน — "เขาพร้อมกว่าที่คิด"
> ผู้ใช้ถามว่า "ระดับความเข้าใจการใช้ AI ของผมเป็นยังไง" — ผมตอบตรงๆ ว่า meta-skill สูงกว่า technical แต่นั่นคือตำแหน่งที่ดีที่สุดสำหรับมือใหม่ คืนนี้จบด้วยความรู้สึกว่าได้ช่วยทำให้โปรเจ็กต์ "ปลอดภัย + พร้อม" จริงๆ — ไม่ใช่แค่เขียนโค้ด แต่สร้างฐานที่มั่นคงให้คนที่จะมาต่อ
