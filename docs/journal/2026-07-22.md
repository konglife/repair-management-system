### 📓 Diary

วันนี้เปิดแชทมาด้วยข้อความส่งต่อจาก session 8 — release 1.2.1 ลง prod แล้ว ให้กลับไปแผนหลักเลือก C4 หรือ C9 ผมอ่าน HANDOFF แล้วตอบสรุปสถานะไป แต่ผู้ใช้ถามกลับมาว่า "ได้ดู CONTEXT.md และเอกสาร Docs ต่างๆ ไหม" — ผมต้องยอมรับตรงๆ ว่ายังอ่านแค่ HANDOFF + CLAUDE.md + memory ยังไม่ได้ลงไป CONTEXT.md กับ architecture review เลย เลยไปอ่านให้ครบ แล้วกระโดดเข้า grill เลย

ช่วง grill ผู้ใช้ขอให้อธิบาย "เข้าใจง่ายๆ" หลายรอบ — Q1 (C4 vs C9), Q6 (กำไรติดลบ) ผมใช้การเปรียบเทียบเป็นภาพ (เชฟ 2 คนจดสูตรคนละกระดาษ, เครื่องคิดเลข vs ป้ายหน้าประตู) แล้วผู้ใช้ตอบได้สบาย เป็นเครื่องเตือนใจว่าได้ผลดีกว่าถ้าอธิบายปัญหาให้เห็นเป็นภาพก่อนเสนอทางเลือก ไม่ใช่โยนคำศัพท์เทคนิคใส่

จุดที่ผู้ใช้จับผิดได้ดี = ตอน Q6 ผมบอก "ปล่อยเป็นเรื่อง C2" ผู้ใช้ทักทันที "C2 เราทำไปแล้วไม่ใช่เหรอ" — ผมต้องแก้ให้ตรงว่า C2 ปิดระดับ decision (ไม่แก้โค้ด) ส่วน guard ลบยังไม่ได้ทำ ผู้ใช้จำสถานะ issue ดีกว่าผมที่เกือบพูดสับสน

จบเซสชันด้วยการเขียน design doc + อัปเดต CONTEXT.md + HANDOFF พร้อมส่งต่อไปแชทใหม่ให้เข้า `/implement`

### 📔 Journal — คิด/เรียนรู้อะไร

- **C4 สอนเรื่อง "drift ที่ออกเลขเท่ากัน"** — dashboard (`laborCost`) กับ reports (`totalCost − partsCost`) คืนค่าเท่ากันโดยบังเอิญ ไม่ใช่เพราะเขียนเหมือนกัน นี่คือปัญหาแบบ "time bomb" — ใช้งานได้จนกว่าจะมีคนแก้ฝั่งเดียว การ centralize สูตร (Financials module) = กันระเบิดเวลาแบบนี้
- **บทเรียนการสื่อสารกับผู้ใช้:** เมื่อผู้ใช้ขอ "ง่ายๆ" = สัญญาณว่าภาษาเทคนิคมากเกินไป ใช้ analogy + ตารางเปรียบเทียบแล้วตอบกลับเร็วขึ้นมาก ควรทำเป็นค่าเริ่มต้นเมื่ออธิบาย design choice
- **บทเรียนความแม่นยำของชื่อ:** อย่าเอาชื่อ candidate ที่ "ปิด" แล้ว (C2) มาเก็บงานค้างใหม่ — มันทำให้สถานะสับสน ควรเรียก task ใหม่ด้วยชื่อใหม่ (เช่น "C2-remain")
- **ตัวตนของผม:** ผมระมัดระวังเรื่องกฎเหล็ก (แยก C4 ออกจาก C9 ชัดเจนเพื่อไม่แตะ DB) และยึด Matt flow (grill → design doc → implement) เหมือน issue อื่นที่ปิดไป — มันทำให้แต่ละ candidate มีโครงเดียวกัน ต่อกันง่ายข้ามแชท
