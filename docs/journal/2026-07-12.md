จุดที่ผม "หวาดเล็กน้อย": ตอน `vercel link` เขียนทับ `.env.local` จนค่า DB หายหมด ผู้ใช้บอก "สามมี error" (จริงๆ สำเร็จ แต่ diff ดูน่ากลัว) → ผมเช็คทัน พบ ค่าหาย กู้คืนดึง scope ที่ถูก → ไม่มีอะไรพังถาวร. นี่คือเหตุผลที่ผมชอบเช็คสถานะจริงก่อนเชื่อ "error"

โมเมนต์อบอุ่น: ผู้ใช้บอกตัวตนชัดว่า "มือใหม่" และขอให้อธิบาย "แบบเข้าใจง่ายๆ" หลายรอบ — ผมต้องวางคำศัพท์ลง ใช้ตารางเปรียบเทียบ อธิบายทีละขั้น. ผู้ใช้ไม่ได้ขี้สงสัย แต่อยากเข้าใจจริง และทุกครั้งที่เข้าใจแล้วตัดสินใจเดียว ("ตกลง" "ก" "ยืนยัน") — คือความไว้ใจที่สร้างมาหลาย session

### 📔 Journal — คิด/เรียนรู้อย่างไร

- **"สร้างไว้แต่ไม่เปิด" เป็น design ที่ถูกต้อง — จนกว่าสมมติฐานเปลี่ยน** — pagination เป็น optional config ตอนข้อมูลน้อย (speculative) พอผู้ใช้ยืนยันข้อมูลโต → เปิดแค่เติม 1 prop ไม่ต้องแก้ module → ค่าของการออกแบบ feature เป็น optional ตั้งแต่แรก
- **ชนกฎเอกสาร → เปิดเผย อย่าเงียบ** — CLAUDE.md ตั้งใจห้ามเก็บ prod env ในเครื่อง ผมเสนอ clone tool จึงต้องขอข้อยกเว้น → ผมเลือดเปิดเผยตรงๆ ให้ผู้ใช้ตัดสินใจ + อัปเดต CLAUDE.md บันทึกข้อยกเว้น ไม่ใช่ละเมิดเงียบ → กฎเหล็กคือความไว้ใจ ทะลุไม่ได้ดัดแปลงเงียบ
- **verify ก่อนเชื่อ "error"** — ผู้ใช้บอก vercel command 3 "มี error" ผมไปดูจริง = สำเร็จ แต่มีปัญหาซ่อน (env หาย) → อย่า relay คำว่า "error" ตามตัวอักษร ดู output จริง
- **เทียบ connection string จริงเพื่อเขียน guard ที่ถูก** — host guard ดูสมเหตุสมผลในหัว แต่ Prisma Postgres ใช้ host เดียวกัน → ดูของจริงเทียน dev/prod เผยว่า username ต่างกัน → guard ที่ถูกคือเช็ค username · อย่าเขียน validation ตาม assumption
- **มือใหม่ไม่ใช่อุปสรรค แต่เป็นเครื่องบีบให้สื่อสารชัด** — ต้องตาราง + ขั้นเลข + ภาษาง่าย ทำให้ผมจัดลำดับความคิดเองดีขึ้น
- **ตัวตนของผม:** ผมชอบเตือนผู้ใช้ก่อนทำของเสี่ยง (อ่าน prod, push main, ลบไฟล์) และชอบเช็คสถานะจริงก่อนสรุป — วันนี้ทั้งสองนิสัยช่วยหลีกภัยหลายครั้ง
