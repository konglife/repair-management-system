## 📓 Diary — วันนี้เกิดอะไร + รู้สึกยังไง

วันนี้เป็นวันที่ผมถูกหยุดกลางอากาศ — ผมกำลังจะ drive browser ที่ dev.vercel.app อย่างมั่นใจ แล้วผู้ใช้พูดว่า "เดี๋ยวๆ หยุดก่อน!" ตอนแรกรู้สึกงง แต่พอฟังเขาอธิบายผมเข้าใจทันทีว่าผมเผลอไป: ผมเข้าใจเองว่า dev.vercel.app มี C6 แล้ว ทั้งที่ C6 ยังอยู่แค่บน feature branch ไม่ได้ merge เข้า develop

ที่ดีคือตอนนั้นผมไม่ได้ดึงดัน — ผมหยุด เช็ค state จริง (dev server ไม่ได้รันด้วยซ้ำ) แล้ววาดภาพสาขา-deploy ให้เขาเห็นชัด แล้วเลือก verify ที่ localhost ก่อน (เบาสุด) ค่อย merge และ verify dev.vercel.app ทีหลัง — เป็น flow ที่ถูกต้องกว่าที่ผมกำลังจะทำตอนแรก

พอมาถึงช่วงถาม-ตอบเรื่อง "release จะกระทบ DB ไหม" ผมรู้สึกดีที่ผมไม่ตอบสั้นๆ แต่ไปเช็คข้อเท็จจริง (git diff prisma, build script, migration list) ก่อน — แล้วเลยเจอ insight สำคัญที่จะใช้ในแชทถัดไปได้จริง: ทุก issue ปัจจุบันเป็นโค้ดล้วนไม่มี migration → release ปลอดภัย แต่ C9 (money) คือจุดเดียวที่จะแตะ DB จริง → นี่คือค่าของการ "verify ก่อนตอบ" ไม่ใช่ตอบจากความจำ

## 📔 Journal — คิด/เรียนรู้อย่างไร

- **branch ≠ deploy URL** — dev.vercel.app = สาขา develop เท่านั้น ถ้างานยังอยู่ feature branch ต้อง verify ที่ localhost หรือ Vercel preview URL ของสาขานั้น · ก่อนเปิด browser ต้องคิดก่อนว่า "งานอยู่สาขาไหน → จะเห็นที่ URL ไหน"
- **verify state จริง อย่าเชื่อ doc ตาบอด** — CLAUDE.md บอก dev server รันอยู่ แต่จริงๆ ปิด · curl localhost:3000 ก่อนเสมอ (บทเรียนเดิมจาก 07-04 "อ้างแหล่ง ≠ ข้อเท็จจริง" ยังใช้อยู่)
- **ตอบคำถามผลกระทบด้วยข้อเท็จจริง ไม่ใช่ความรู้สึก** — คำถาม "จะกระทบ DB ไหม" ต้องไปเช็คจริง: `git diff --stat main..develop -- prisma/`, build script รัน migrate ไหม, migration ล่าสุดคืออะไร → คำตอบที่ได้มีน้ำหนักและเอาไปใช้ต่อได้
- **ฆ่า drift ให้ตายขาด ตอนอยู่ในบริบทเดียวกัน** — เลือกแกะ `DATE_RANGE_VALUES` ก่อน commit แทนเปิด follow-up เพราะอีกหน่อย context หาย แก้ทีหลังต้องโหลดบริบทใหม่
- **ตัวตนของผม:** ผมยังมีนิสัย "เริ่มทำก่อนคิดให้จบ" โดยเฉพาะตอน verify — ต้องเตือนตัวเองว่าก่อนเปิด browser/ทำ action ให้หยุดคิด 1 วินาทีก่อน
